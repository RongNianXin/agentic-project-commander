# Codex 切换账号后旧对话无法继续

## 一、问题现象

在 Codex 中切换官方账号、API Key 或中转站供应商后，可能出现以下现象：

- 新建对话可以正常收到 AI 回复。
- 历史对话仍然显示在列表中，但发送新消息后失败。
- 常见错误类似：

```text
The encrypted content for item cmp_xxx could not be verified.
Reason: Encrypted content could not be decrypted or parsed.
```

- 某些任务是在 Codex 崩溃、断点恢复或“上下文压缩”期间出问题。
- 使用 CC-Switch 的“统一 Codex 会话历史”后，官方和第三方任务虽然能出现在同一个列表中，但跨供应商继续任务时仍可能报上述错误。

这不是“整个聊天记录消失”，而是“新供应商无法使用旧供应商留下的一部分加密状态”。用户消息、AI 可见答复和工具调用通常仍在本地任务文件中。

## 二、问题原因（通俗版）

### 1. “看得见任务”和“能继续任务”是两件事

Codex 使用 `model_provider` 给任务分类。CC-Switch 把官方和第三方供应商统一到 `custom` 分类后，可以让它们出现在同一个历史列表中。

但是，这只解决了“列表是否显示”，没有解决“加密内容是否能被新供应商解密”。

### 2. 历史任务中存在供应商绑定的加密状态

Codex 会在任务文件中保存 `encrypted_content`。这些内容主要用于隐藏推理状态和上下文压缩状态，并不是普通聊天文字。

这类密文通常只能由生成它的原账号或原后端正确验证。任务从供应商 A 切换到供应商 B 后，B 收到 A 的密文，就可能拒绝请求。

### 3. 上下文压缩时崩溃可能让问题更明显

本次问题中，曾发生 Codex 崩溃时正在压缩上下文。这个时间点可能留下旧的或不兼容的压缩密文。

这属于本次问题的相关因素，但不能仅凭时间点断言它是唯一原因。即使没有崩溃，只要跨账号或跨后端重放供应商绑定的密文，也可能发生同类错误。

### 4. `model_provider = "custom"` 不能转换密文

把官方供应商也标记为 `custom`，只能统一历史列表分类，不能把供应商 A 的密文转换成供应商 B 可以解密的密文。

因此：

- 历史列表统一：由 `model_provider` 和状态数据库决定。
- 历史任务能否跨供应商继续：由任务里是否还包含不兼容的 `encrypted_content` 决定。

二者必须分开排查。

## 三、本次经过验证的解决思路

核心办法是：

> 在 Codex 和 CC-Switch 完全退出时，备份真实任务文件，删除无法跨供应商使用的隐藏推理/压缩密文，同时严格保留用户可见对话和其他结构，然后再启动 Codex。

这不是“解密密文”，而是舍弃不可移植的隐藏状态，让 Codex 根据仍然保留的可见历史重新建立当前供应商可用的上下文。

## 四、安全修复流程

### 阶段 A：只在副本中模拟

在 Codex 仍运行时，只允许执行只读扫描和工作目录副本转换，不得改动真实任务。

扫描范围：

```text
%USERPROFILE%\.codex\sessions
%USERPROFILE%\.codex\archived_sessions
```

只识别正式任务文件：

```text
rollout-...-UUID.jsonl
```

不要把名称中带有 `.backup...jsonl` 的旧手工备份误认为正式任务。

当前正在运行的任务必须从模拟范围中排除。

### 阶段 A 的删除规则

只删除包含 `encrypted_content` 的以下内容：

1. 顶层 `response_item` 中，`payload.type` 为 `reasoning` 的记录。
2. 顶层 `response_item` 中，`payload.type` 为 `compaction` 的记录。
3. 数组中同类型的加密 `reasoning` 或 `compaction` 项。
4. 旧格式 `type: "encrypted_content"` 加密块。

不得删除：

- 用户消息。
- AI 可见答复。
- 工具调用和工具结果。
- 任务元数据。
- 普通上下文内容。
- 不包含密文的未知结构。

如果发现无法归类的 `encrypted_content`，必须停止，不得猜测删除。

### 阶段 A 的验证条件

每个候选文件必须同时满足：

1. 原始文件和候选文件都能逐行解析为合法 JSON。
2. 候选文件中的 `encrypted_content` 数量为 0。
3. 删除数量与已识别的推理、压缩和旧格式加密块数量完全相符。
4. 对所有保留字段计算稳定摘要，迁移前后摘要和数量完全一致。
5. 转换期间原始文件的大小和 SHA-256 不得发生变化。
6. 任一条件失败时拒绝安装。

### 阶段 B：离线安装

阶段 B 会修改真实任务，所以必须先：

1. 等所有长任务完成。
2. 完全退出 Codex，包括后台进程和系统托盘。
3. 完全退出 CC-Switch，包括系统托盘。
4. 确认没有 `ChatGPT.exe`、`codex.exe`、`codex-code-mode-host.exe`、`codex-command-runner...exe` 或 `cc-switch.exe` 运行。

安装器应当采用以下事务顺序：

1. 重新扫描安装时的现场，不直接照搬旧模拟结果。
2. 为全部受影响任务生成候选文件。
3. 完整验证所有候选文件。
4. 备份每个原始任务并校验 SHA-256。
5. 同时备份 Codex 配置、状态数据库和 CC-Switch 数据库。
6. 提交前再次确认原始文件没有变化。
7. 使用“原文件改名为回滚文件，候选文件改名为正式文件”的方式逐个原子替换。
8. 恢复并验证原文件的访问时间、修改时间和文件权限，避免历史任务被错误排到最新位置或访问边界变化。
9. 每提交一个文件就更新 `manifest.json`。
10. 任一步失败，自动恢复已经提交的文件。

不要使用会直接覆盖整个目录、删除历史或修改正在运行任务的 PowerShell 脚本。

## 五、本次实际执行结果

本次使用的批量迁移备份：

```text
<USER_HOME>\Documents\Codex\CodexSessionBackups\bulk-<TIMESTAMP>
```

实际结果：

- 扫描正式任务：475 个。
- 需要迁移并安装：441 个。
- 已备份：441 个。
- 已提交：441 个。
- 状态：`installed`。
- 辅助配置/数据库备份：5 个。
- 备份总计：447 个文件，约 3.66 GB。
- 缺失的源文件或备份：0。
- 安装后迁移临时文件残留：0。

清单文件：

```text
<USER_HOME>\Documents\Codex\CodexSessionBackups\bulk-<TIMESTAMP>\manifest.json
```

安装后抽查的两个任务都能继续推进，JSONL 文件结构合法，原来的解密错误没有再次出现。

## 六、为什么第一次断点恢复很慢

本次一个大型任务迁移前约 365 MB，恢复后约 371.5 MB，原有 8,255 行记录、1,509 个加密字段和 15 个加密压缩节点。

删除旧压缩密文后，Codex 可能需要从较长的可见历史重新建立当前供应商的上下文，所以首次恢复花费几十秒到数分钟是可以解释的。

界面出现“重新连接 5/5”还可能包含网络重试，因此不能把全部等待时间都归因于本地迁移。只要最终继续生成、文件仍为合法 JSONL，且没有再次出现解密错误，就说明修复主路径有效。

## 七、重要限制：本次修复不是永久自动防复发

任务恢复后，当前供应商会继续生成新的 `encrypted_content`。本次抽查发现，两个已恢复任务又分别新增了 6 个和 3 个加密推理字段。

这意味着：

- 在同一供应商下继续，一般没有问题。
- 再次切换到其他账号或后端时，新生成的密文仍可能导致同样的错误。
- 一次批量迁移只能清理执行当时已经存在的密文，不能阻止以后产生新的密文。

在自动化方案完成前，每次跨账号或跨供应商切换都应执行以下临时流程：

1. 等所有任务停止运行。
2. 完全退出 Codex。
3. 完全退出 CC-Switch。
4. 再次运行经过验证的批量迁移工具。
5. 确认显示 `Migration completed` 和新的备份目录。
6. 启动 CC-Switch，完成供应商切换。
7. 再启动 Codex，打开原任务并发送一条短消息验证。

只要仍有任务在运行，就不要执行迁移，也不要切换供应商。

## 八、计划中的永久方案

真正覆盖“以后 CC-Switch 新增任何令牌”的方案，应修改 CC-Switch 的通用 Codex 供应商切换入口，而不是为每个令牌单独写配置。

建议的切换事务如下：

1. 用户点击任意 Codex 供应商。
2. CC-Switch 检查 Codex 是否仍在运行。
3. 如果 Codex 在运行，拒绝切换，并提示用户先退出 Codex。
4. 如果 Codex 已退出，扫描所有正式任务中的加密推理/压缩记录。
5. 对受影响任务生成带 SHA-256 校验的增量备份。
6. 在副本中清理并验证。
7. 原子提交任务迁移。
8. 迁移成功后才写入新供应商配置并完成切换。
9. 任一步失败时保持原供应商不变，并自动回滚。

因为逻辑位于“通用 Codex 切换入口”，后续新增的官方账号、API Key 和中转站令牌都能走同一流程，不需要逐个修改脚本。

截至本文记录时，这个 CC-Switch 自动切换钩子尚未安装。不得把它描述为已经完成。

## 九、CC-Switch 配置注意事项

### 官方供应商

推荐做法：

- 开启 CC-Switch 的“统一 Codex 会话历史”。
- 让 CC-Switch 在运行时为官方供应商注入共享的 `custom` 分类。
- 不要在官方供应商的持久配置中手工长期写入一套指向第三方地址的 `[model_providers.custom]`。
- 官方认证继续使用官方登录材料，不要把官方流量错误路由到中转站。

如果当前机器依赖手工 `model_provider = "custom"` 才能显示统一历史，不要在任务运行期间修改。应先备份，再检查 CC-Switch 的统一历史开关、实时配置注入和 `state_5.sqlite` 中的供应商分类是否一致。

### API 和中转站供应商

- 通过 CC-Switch 正常新增供应商。
- 不要为每个供应商创造不同的历史分类；统一历史场景应使用稳定的 `custom` 分类。
- `base_url`、API Key、模型映射按该供应商实际要求填写。
- 不要把 API Key、访问令牌或刷新令牌写入故障文档、截图或聊天消息。
- 新增供应商能进入同一列表，不代表它能解密其他供应商留下的密文；切换前清理仍然必要。

## 十、正确备份和恢复

### `config.toml` 不是聊天历史

`config.toml` 主要保存 Codex 配置，不是一段配置对应一条对话。只备份它，不能完整备份聊天历史。

Codex 历史主要涉及：

```text
%USERPROFILE%\.codex\sessions
%USERPROFILE%\.codex\archived_sessions
%USERPROFILE%\.codex\state_5.sqlite
%USERPROFILE%\.codex\state_5.sqlite-wal
%USERPROFILE%\.codex\state_5.sqlite-shm
```

配置和认证还可能涉及：

```text
%USERPROFILE%\.codex\config.toml
%USERPROFILE%\.codex\auth.json
%USERPROFILE%\.cc-switch\cc-switch.db
%USERPROFILE%\.cc-switch\cc-switch.db-wal
%USERPROFILE%\.cc-switch\cc-switch.db-shm
%USERPROFILE%\.cc-switch\settings.json
```

### 正确备份方法

1. 完全退出 Codex 和 CC-Switch。
2. 新建一个带时间戳的备份目录，不覆盖上一代备份。
3. 复制任务目录、索引数据库、配置和 CC-Switch 数据库。
4. 为文件生成 SHA-256 清单。
5. 保存备份时间、Codex 版本、CC-Switch 版本和当前供应商说明。
6. 备份目录应限制访问权限；认证文件含敏感令牌，不应随意上传云盘或分享。

### 恢复时会不会丢掉备份时间点之后的新对话

如果直接用旧备份覆盖整个 `sessions`、`archived_sessions` 和状态数据库，那么备份时间点之后新增的任务或消息可能丢失。

正确恢复方式：

1. 先完整备份“恢复前现场”。
2. 不要直接清空当前任务目录。
3. 优先按任务 UUID 恢复单个损坏任务。
4. 如果必须恢复整个快照，应先把快照之后新增的任务识别并另行保存。
5. 恢复任务文件后，同步检查 `state_5.sqlite` 索引。
6. 恢复完成后核对任务数量、文件哈希和最近消息。

因此，备份应采用“多代快照 + 选择性恢复”，而不是始终覆盖同一个备份目录。

## 十一、出现问题时的停止条件

出现以下任一情况，必须停止修改并保留现场：

- Codex 或 CC-Switch 仍在运行。
- 任务文件正在增长或修改时间持续变化。
- JSONL 存在无法解析的行。
- 出现无法归类的 `encrypted_content`。
- 候选文件仍包含加密字段。
- 保留字段摘要不一致。
- 原始文件在扫描、备份或提交期间发生变化。
- 备份哈希与原始文件不一致。
- 状态数据库正在写入或 WAL 文件仍快速变化。

不要用删除整个 `.codex` 目录、覆盖全部历史、清空状态数据库或强制结束迁移进程的方式“试错”。

## 十二、给后续 AI 的最短处理原则

1. 先确认是“列表不可见”还是“密文不可解”，不要混为一谈。
2. 当前任务运行时只做只读检查和副本模拟。
3. 不读取或展示用户令牌。
4. 不直接编辑真实 JSONL。
5. 只删除经过分类的加密推理/压缩状态。
6. 用保留字段摘要证明可见历史没有变化。
7. 安装必须离线、先备份、逐文件原子提交、可回滚。
8. 修复后必须说明新密文仍会产生，除非自动切换钩子已经真正实现并验证。
