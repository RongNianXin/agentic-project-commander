# Codex 对话无法归档：Windows 扩展路径兼容性故障

## 一、结论先行

本次两个任务无法归档的共同根因已经通过单变量实验确认：

```text
state_5.sqlite / threads / rollout_path
```

保存成了 Windows 扩展路径：

```text
\\?\<CODEX_HOME>\sessions\...\rollout-<TASK_ID>.jsonl
```

当前测试版本的 Codex `thread-store` 可以读取这个文件，却不能在归档流程中正确处理这种路径表示，最终把路径处理失败包装为：

```text
failed to archive session:
thread-store internal error:
failed to archive thread:
系统找不到指定的文件。 (os error 2)
```

这里的“找不到文件”具有误导性。两个案例的 JSONL 源文件都真实存在；故障点是数据库中的路径表示与归档实现不兼容，不是用户删除了聊天文件。

修复原则是：

1. 先做 SQLite 一致性备份和目标 JSONL 备份。
2. 只把目标任务这一行的 `rollout_path` 从 `\\?\C:\...` 规范化为 `C:\...`。
3. 仍由 Codex 自带的 `archive` 命令执行正式归档，不手工搬运会话文件。
4. 回读数据库、归档文件和应用归档列表，不能只看命令退出码。

配套工具：[Repair-CodexThreadArchive.ps1](Repair-CodexThreadArchive.ps1)

## 二、两个窗口的问题是否相同

| 现象 | 案例 A：总指挥任务 | 案例 B：已废弃工具任务 |
| --- | --- | --- |
| 当时能否继续对话 | 用户观察为不能；应用查询时为 `notLoaded` | 能，最后一轮可正常完成 |
| 能否归档 | 不能 | 不能 |
| 归档错误 | `thread-store` / `os error 2` | 同一错误 |
| JSONL 是否真实存在 | 存在 | 存在 |
| 数据库路径 | 带 `\\?\` | 带 `\\?\` |
| 规范化路径后归档 | 成功 | 成功 |

因此要分成两层理解：

- **共同的归档故障相同**：两者都是 `rollout_path` 扩展路径兼容性问题。
- **对话能力不同**：案例 B 的会话运行链正常；案例 A 当时出现无法继续的独立现象。

案例 A 后续记录中仍出现了正常完成的用户回合，且可见回合没有 `systemError`。所以现有证据不能把 `notLoaded` 解释成永久损坏，也不能证明它由归档路径引起。`notLoaded` 只表示应用当时没有把任务加载进运行内存；“为何某次发送失败”的确切触发点仍属「待确认」。

换句话说：本次已经彻底定位并修复的是两个任务的归档问题；案例 A 曾经不能对话属于另一条因果链，不能为了给出完整答案而编造根因。

## 三、根因是怎样证明的

### 1. 先排除常见原因

已逐项确认：

- 归档请求发生时没有活动回合，`had_active_turn=false`。
- 两个目标 JSONL 都在 `$CODEX_HOME/sessions` 中真实存在。
- `$CODEX_HOME/archived_sessions` 已存在，其他任务可正常归档。
- 两个目标都存在 `session_index.jsonl` 记录和 `state_5.sqlite.threads` 行。
- 任务未置顶；标题特殊字符不是共同原因。
- 桌面界面和同版本 CLI 都返回相同错误，因此不是侧栏按钮或 RPC 包装层故障。
- `migrate-rollouts` 的 `eligible` 不是原因：故障任务、正常任务和已归档样本都可能显示该状态。

### 2. 找到唯一稳定差异

故障前的状态库中：

- 两个失败任务的 `rollout_path` 都带 `\\?\`。
- 正常归档样本使用普通盘符路径。
- 97 个未归档任务使用扩展路径。
- 137 个已归档任务全部使用普通路径，没有一个保留扩展前缀。

扩展路径和去掉前缀后的普通路径都能访问同一个文件，文件大小一致。由此排除了“源文件真的不存在”。

### 3. 做单变量实验

对案例 B 只修改一个字段：

```text
修改前：\\?\C:\...\rollout-<TASK_ID>.jsonl
修改后：C:\...\rollout-<TASK_ID>.jsonl
```

没有改 JSONL 内容，没有预先改 `archived` 标记，也没有手工移动文件。

结果：同一版本 CLI 在修改前稳定失败，修改后立即归档成功。随后对案例 A 重复同一流程，也从同一错误转为成功。

这是因果验证，不只是相关性观察。

## 四、`\\?\` 是什么，为什么会出错

`\\?\` 是 Windows 的扩展长度路径前缀，通常用于绕过传统路径长度解析。它本身是合法路径格式。

本次故障不是“Windows 不认识该路径”，而是 Codex 当前归档实现中的某一步没有保持这种路径格式的一致性。可能表现为：源路径查找使用扩展形式，目标路径拼接、父目录判断或数据库更新使用普通形式，最终在文件移动阶段得到 `os error 2`。

可以确认的边界：

- 扩展路径记录跨越多个历史 Codex 版本，不只出现在单一版本。
- 当前样本中的扩展路径全部来自桌面集成记录，但桌面集成也产生了大量普通路径；所以“使用桌面版”不是充分原因。
- 路径长度不是充分原因；大多数异常记录的工作目录并不长。
- 当前数据库没有保留“哪一次写入把普通路径改成扩展路径”的审计历史。

因此，**最初是谁在什么时刻写入 `\\?\` 仍属「待确认」**。现有证据支持“Codex 桌面端的会话发现、规范化或状态库回填路径产生了两种表示”，但不足以精确指向创建、恢复、Fork、升级或异常退出中的某一步。

这里应把两层结论分开：

- 归档失败的直接根因：已确认。
- 异常路径最初的写入触发器：待确认，需要产品源码日志或上游修复说明。

## 五、以后如何自己修复

### 前提

- 仅适用于 Windows。
- 错误必须包含 `thread-store` 和 `os error 2`。
- 目标任务必须已经停止运行。
- 需要 Node.js 22 或更高版本。
- 脚本只修复数据库路径恰好以 `\\?\<盘符>:\` 开头、且扩展/普通路径都能找到源文件的任务；其他情况会拒绝修改。

### 1. 找到任务 ID

在 Codex 中打开目标任务，任务 URL、开发者信息或诊断工具中可看到 UUID 形式的任务 ID：

```text
00000000-0000-0000-0000-000000000000
```

不要把任务标题当作 ID。

### 2. 先做只读诊断

在本目录打开 PowerShell：

```powershell
.\Repair-CodexThreadArchive.ps1 -TaskId '<TASK_ID>' -DryRun
```

目的：确认是不是本文已经验证的扩展路径故障。

预期结果：

```text
诊断命中：rollout_path 带有 Windows 扩展路径前缀，且源文件实际存在。
DryRun 完成：未修改数据库，也未执行归档。
```

异常处理：

- “不是已知的 Windows 扩展路径故障”：停止，不要强改数据库。
- “文件没有同时存在”：停止，不要创建空 JSONL 或占位文件。
- “找不到状态数据库”：检查 `$CODEX_HOME` 是否被自定义；必要时用 `-CodexHome` 指定。
- “Node.js 版本过低”：升级 Node.js，或使用具备 Node.js 22+ 的 Codex 终端。

### 3. 执行修复和归档

```powershell
.\Repair-CodexThreadArchive.ps1 -TaskId '<TASK_ID>'
```

脚本会自动：

1. 用 SQLite `VACUUM INTO` 创建一致性数据库备份。
2. 备份目标任务的 JSONL 并计算 SHA-256。
3. 用带旧值条件的 SQL 只更新目标行，避免覆盖并发变化。
4. 优先找到桌面端正在使用且可执行的 Codex CLI。
5. 调用 `codex archive <TASK_ID>`。
6. 验证 `archived=1`、`archived_at`、归档文件存在、活动源文件消失。
7. CLI 失败且任务仍未归档时，自动恢复原路径记录。

成功时会显示：

```text
归档成功：数据库标记、归档时间、归档文件和源文件迁移均已验证。
```

### 4. 在应用中复核

操作：打开 Codex 的已归档任务列表，搜索原任务标题。

目的：确认桌面应用也能读取归档结果。

预期结果：目标不再出现在活动列表，并出现在已归档列表；需要时可以取消归档恢复。

异常处理：若脚本成功但界面未刷新，重启 Codex 后再检查一次。不要再次运行脚本。

## 六、脚本的安全边界

工具刻意采用失败关闭策略：

- 不批量修改数据库。
- 不按标题查找，必须输入精确任务 ID。
- 不处理普通路径对应的其他归档错误。
- 不处理 UNC 扩展路径 `\\?\UNC\...`。
- 不创建缺失的会话文件。
- 不手工把 JSONL 移到归档目录。
- 不直接伪造 `archived=1`。
- 不运行 `migrate-rollouts --apply`。

若 Codex 命令返回失败，但已经发生部分归档状态变化，脚本不会强行回滚，因为只恢复数据库字段可能造成数据库与文件再次不一致。此时应保留脚本输出的备份目录并停止重复操作。

## 七、为什么不采用其他修法

### 只重启 Codex

重启可能刷新界面状态，但不会把数据库中的 `\\?\` 改成普通路径。两个案例在不同入口重复归档均稳定失败，所以重启不是根治。

### 手工移动 JSONL

归档还需要同步数据库标记、归档时间和应用索引。只移动文件会制造新的不一致。

### 直接把 `archived` 改成 1

这只伪造状态，不会完成官方定义的日志文件迁移。

### 运行 `migrate-rollouts --apply`

对照实验表明，正常任务和已归档任务也可能被报告为 `eligible`。这项迁移与本故障没有充分因果关系，不能作为修复。

### 批量去掉全部 97 条路径前缀

没有必要，也会扩大风险。应在某个任务实际出现同一错误时，先 `-DryRun`，再只修复该任务。

## 九、官方资料与证据边界

- [OpenAI Codex App Server](https://developers.openai.com/codex/app-server)

官方文档确认：`thread/archive` 会把任务的持久化 JSONL 日志移动到归档目录，并在成功时返回空对象。官方公开资料没有说明本次 Windows `\\?\` 兼容性错误，也没有提供修改私有 SQLite 状态库的官方修复程序。

因此，本文的根因与修复来自本机双案例复现、路径存在性检查、同版本 CLI 对照和单变量实验。Codex 私有数据库结构可能在后续版本变化；脚本遇到字段或条件不符时应停止，而不是猜测修改。
