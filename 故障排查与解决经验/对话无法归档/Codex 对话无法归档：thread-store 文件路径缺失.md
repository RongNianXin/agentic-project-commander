# Codex 对话无法归档：thread-store 文件路径缺失

## 一、文档目的

本文根据一次已脱敏的双任务归档故障整理，目标是帮助用户区分：

1. 对话无法继续和对话无法归档是否属于同一故障。
2. 归档失败究竟发生在界面、任务运行状态，还是本地会话存储层。
3. 再次遇到类似问题时，如何通过最少步骤自行判断，并保留可继续调查的证据。

本文记录的是当前案例中已经复现的行为。Codex 内部会话格式和状态字段不是稳定的公共接口，后续版本是否仍有相同行为属于「待确认」。

## 二、故障现象

本次涉及两个任务，以下统一称为案例 A 和案例 B：

| 案例 | 能否继续对话 | 能否从界面归档 | 应用状态 |
| --- | --- | --- | --- |
| A | 不能 | 不能 | `notLoaded` |
| B | 能 | 不能 | 最后一轮完成后为 `idle` |

两个案例表面相似，但对话能力明显不同，因此最初不能直接假设它们是同一种故障。

## 三、排查过程

### 1. 只读检查任务状态

先读取任务列表和各任务最近的回合状态，不执行归档：

- 案例 A 被标记为 `notLoaded`。
- 案例 B 在回复过程中一度是 `active`，回复完成后恢复为 `idle`。
- 两个任务都没有被置顶。

这一阶段只能说明对话运行状态不同，不能证明归档失败是由 `active`、`idle` 或 `notLoaded` 引起的。

### 2. 回读历史回合

对两个任务的历史回合做只读统计：

- 案例 A 的可见历史回合均为 `completed`，没有记录到 `systemError`。
- 案例 B 存在少量 `interrupted` 历史回合，但最新回合已经正常 `completed`，且没有错误对象。

因此，没有证据支持“最后一次模型回复失败，所以无法归档”。历史中断也不能单独证明归档故障。

### 3. 执行受控归档实验

在用户明确授权后，从一个健康任务分别调用 Codex 内置归档能力，避免只依赖侧栏菜单。

两个目标都返回完全相同的错误：

```text
failed to archive session:
thread-store internal error:
failed to archive thread:
系统找不到指定的文件。 (os error 2)
```

这一步把故障从“界面按钮没有反应”定位到了本地 `thread-store` 归档流程。

### 4. 检查归档库是否存在

随后只读列出已经归档的任务，确认归档库中存在其他历史记录。

因此，现有证据不支持“整个归档库从未建立”。更可能的情况是：归档这两个任务时，`thread-store` 引用的某个源文件、目标路径或索引映射已经不存在。

## 四、已确认结论

### 1. 两个任务的归档根因相同

归档失败发生在 `thread-store` 文件操作层，直接错误是：

```text
os error 2：系统找不到指定的文件
```

这不是标题中含特殊字符、任务被置顶或用户操作顺序造成的界面问题。

### 2. `active` 不是本次归档失败的根因

案例 B 在最终回复结束后已经恢复为 `idle`，再次调用归档仍返回同一个文件缺失错误。

在任务内部询问“为什么不能归档”时，任务会因为正在回答而自然显示为 `active`。仅凭这一瞬时状态判断“运行中的任务不能归档”会形成循环论证，不能作为根因结论。

### 3. `notLoaded` 只解释案例 A 的对话异常

案例 A 无法继续对话，并被应用标记为 `notLoaded`；这说明它还有独立的加载或运行环境问题。

但案例 B 是 `idle` 且可以继续对话，仍然出现相同归档错误。因此，`notLoaded` 不是两个任务共同的归档根因。

### 4. 当前能确定的是故障层，尚不能确定最初触发点

已经确认：归档流程需要的某个文件路径或索引映射缺失。

尚未确认具体缺少哪一个路径，也没有足够证据判断最初由以下哪种情况触发：

- 会话源文件被移动、删除或改名。
- 线程索引记录的路径与实际文件位置失配。
- 新建任务、交接、Fork 或恢复流程中的持久化缺陷。
- 应用升级、异常退出或同步过程留下不完整状态。
- 其他 Codex 客户端缺陷。

以上都只能列为候选原因，不能写成已确认事实。

## 五、两类现象的区别

| 问题 | 案例 A | 案例 B |
| --- | --- | --- |
| 对话运行层 | `notLoaded`，无法继续 | `idle`，可以继续 |
| 历史回合 | 可见回合均已完成 | 有历史中断，但最新回合已完成 |
| 归档层 | `thread-store` 返回文件不存在 | 同样返回文件不存在 |
| 判断 | 同时存在加载故障和归档存储故障 | 只有归档存储故障得到证实 |

结论是：两者“无法归档”的底层错误相同，但“能否继续对话”的问题不同。

## 六、以后如何自行判断

### 第一步：先判断对话是否还能工作

- 能正常发送并收到回复：对话运行链仍然可用。
- 无法发送、一直加载或任务显示 `notLoaded`：另有加载或运行故障，不要把它直接等同于归档故障。

### 第二步：等待当前回复完全结束

操作：等待停止按钮和运行提示消失，再尝试一次侧栏归档。

目的：排除任务确实仍在执行造成的临时限制。

预期结果：任务从侧栏消失，并可在设置中的已归档任务里找到。

异常处理：结束后仍不能归档，不要继续用“它还在运行”解释，应进入下一步。

### 第三步：从健康任务执行一次受控归档

可以在另一个正常任务中发送：

```text
请先只读确认目标任务已经结束运行，然后只对 <TARGET_TASK_ID> 执行一次归档并返回完整工具回执。不要修改或删除会话文件。
```

归档是状态写操作，执行前应明确指定目标任务。成功归档可以在设置中恢复，不等于删除历史。

### 第四步：根据回执分流

| 结果 | 说明 | 下一步 |
| --- | --- | --- |
| 内置归档成功，但侧栏操作失败 | 归档后端可用，问题在界面或状态同步 | 重启应用并核对已归档列表 |
| 返回 `active` 或仍在运行 | 当前回合尚未结束 | 停止或等待完成后只重试一次 |
| 返回 `os error 2` | 归档所需文件路径不存在或映射失配 | 停止重复点击，保留现场 |
| 返回权限或文件占用错误 | 权限、锁或其他进程占用 | 记录完整错误码后针对性处理 |
| 返回其他内部错误 | 根因待确认 | 保存完整回执，不要根据现象猜测 |

## 七、遇到 `os error 2` 时怎么处理

### 立即操作

1. 保留原任务，不手动删除本地会话文件。
2. 将重要任务的当前目标、已完成项、修改文件、验证结果和下一步写入项目检查点。
3. 对无法继续的任务，使用已有交接记录在新任务中恢复工作。
4. 保存归档工具的完整错误正文和发生时间。

### 不要操作

- 不要为了“补文件”创建空 JSONL、空目录或同名占位文件。
- 不要直接移动 `$CODEX_HOME/sessions` 或 `$CODEX_HOME/archived_sessions` 中的文件。
- 不要编辑线程索引、数据库或会话元数据后立即启动 Codex。
- 不要反复点击归档；重复同一个缺失路径操作不会修复映射。
- 不要把“重启后按钮能点”当成文件映射已经修复，必须回读已归档列表验证。

## 八、如需继续精确定位

要确认究竟缺少哪个文件，需要在 Codex 完全退出后，对单个目标任务执行受控的只读核对：

1. 在 `$CODEX_HOME/sessions` 中定位 `<TARGET_TASK_ID>` 对应的会话文件。
2. 在 `$CODEX_HOME/archived_sessions` 中检查是否存在同 ID 文件或残留目标。
3. 检查线程索引记录的会话路径是否与实际文件一致。
4. 比较一个可正常归档任务的文件位置和元数据结构。
5. 只记录文件是否存在、相对路径、大小、修改时间和脱敏哈希，不读取或公开对话正文。

该步骤涉及 Codex 私有本地状态。必须先备份、限制到单个任务，并把任何修复设计成可回滚操作。没有确认具体缺失路径前，不应直接修改会话文件或索引。

## 九、推荐保存的证据

以后再次遇到归档失败，至少保存：

- 故障发生时间。
- 脱敏后的任务标识，如 `<TARGET_TASK_ID>`。
- 任务当前状态：`active`、`idle`、`notLoaded` 或其他值。
- 最新回合是否完成，是否有错误对象。
- 内置归档调用的完整错误正文。
- 已归档列表是否可以正常读取。
- 应用重启前后结果是否一致。

不要保存或公开真实任务 ID、绝对用户路径、账号、凭据、聊天正文或原始会话文件。

## 十、最终经验总结

1. “不能对话”和“不能归档”必须分层诊断，不能只看侧栏表现。
2. 在任务内部检查状态时，任务会因为正在回答而变成 `active`；该状态不能自动证明归档限制。
3. 界面归档失败时，受控调用内置归档能力可以获得真正的底层错误。
4. 本案例中两个任务共同的归档根因是 `thread-store` 文件路径缺失，而不是运行状态。
5. `os error 2` 已经足以停止盲目重试，但不足以证明具体是源文件、目标路径还是索引中的哪一项缺失。
6. 精确修复前应保留原始现场，并依赖项目检查点或新任务继续工作。
