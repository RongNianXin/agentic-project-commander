# 第二代工作流操作手册

本手册是操作者作为人类唯一需要打开阅读的行为入口。`00、02～10` 和非编号的 `总指挥轻量交接启动配置.md` 是供 AI 按场景自动读取的规则、模板与启动配置；下文每个场景中的“读取文档”表示要让 AI 读取，不要求你再打开、理解或手工整理这些文件。

## 下载后 3 步启动

1. 下载或克隆本仓库到一个稳定的本地目录，确认该目录直接包含 `00～10` 文档和 `总指挥轻量交接启动配置.md`。
2. 在 Codex Desktop 中打开真正要开发或管理的目标项目，而不是本规则仓库；只有维护规则本身时才把本仓库作为目标项目。
3. 复制下方“登记规则文档目录”提示词，把占位符替换为本仓库的本地绝对路径；登记通过后发送“场景 1”，再按需要选择其他场景。

如果 Codex 无权读取规则目录，请先把该目录加入当前可读工作区，或只把 `00～10` 复制到目标项目中已被 Git 忽略的本地规则目录，再登记新路径。目标项目没有合适的状态目录时，AI 可能要求你确认一次 `AI状态索引.md` 的存放位置；应选择项目已有的个人、私有或本地管理目录，并确保它不会被提交到团队仓库。

## 使用者须知
1. 本工作流仅直接适用于 GitHub；其他平台要先单独适配。
2. 打开一个总指挥任务，从下表选择场景并复制提示词；不确定时先用场景 1 恢复事实。不要一次性上传全部规则文档。无论是新任务抉择、开发中的反馈还是任务完成结果，默认都只告诉总指挥，不要同时向专项窗口重复描述。
3. 只填写 AI 无法读取或不能替你决定的内容。轮次、快照、任务 ID、分支和历史截点由 AI 自动处理。
4. `【】` 中是要选择或填写的内容。多个目标或账号用逗号分隔；必填占位符未替换时，AI 必须停止并指出缺项。
5. 开放式字段会在后面提供 `(示例：……)`；示例只帮助理解，不是必须照抄的答案。纯选择题不附示例。
6. 协作开发默认分两步：AI 先只读扫描并生成一张批量执行卡；你集中确认一次后，总指挥在主窗口无人值守执行卡内动作。只有确实能降低整个工作流总 Token 或满足独立审查/能力隔离要求时，才会增加最少量专项任务。
7. 账号只用于识别身份，不自动代表 Assignee、实现者、PR 作者、Reviewer 或远端授权；具体责任必须另行判断。
8. 每项任务结束时，AI 应用 1—2 句人话说明结果和是否需要你操作；需要你参与时，必须给出步骤、目的、预期结果和异常反馈方式。若剩余步骤属于高资源门禁或曾造成卡顿的任务，必须同时给出待授权状态、精确命令、范围、风险、准备事项、终止方式和可直接复制的确认文本，不能只写“之后执行”。收到这类授权卡后，你可以将确认文本原样复制并发送，不需要自行改写命令、补填技术 ID 或另写授权范围。
9. 在 VS Code 中快速浏览小节目录：按 `Ctrl+Shift+O` 打开当前文档的标题列表，输入场景编号或标题即可跳转；需要常驻目录时，选择“查看 → 打开视图 → 大纲”，点击侧边栏标题定位。不要通过破坏标题层级来放大章节标题。
10. 每个编号保留独立状态；“被发现”不等于必须执行或评论。Approve、Merge、Close、部署和不可逆操作仍须遵守单独门禁。
11. 场景 2A、2B、3A、3B 结束时，AI 会自动给出当前行动方、必须人工操作和建议人工操作；2A、3A、3B 还会给出 PR/Issue 关系树，2B 会给出本地基线、检查点、继承远端对象和发布门禁。无需再额外调用场景 4A；只有想重新汇总、补看或怀疑遗漏时才使用场景 4A。
12. 是否继续当前任务由 AI 根据稳定截点、未完成工作、可迁移回执和本地会话日志健康自动判断并提醒。平台在同一任务里多次自动压缩属于正常续行，不要求因此换任务，也不要按固定对话轮数、压缩次数、压缩前 Token 峰值或上下文占比自行切换。AI 能定位本机当前会话文件时应主动告知路径和最近大小；默认达到 `200 MiB` 只提醒评估，达到 `300 MiB` 才在当前原子步骤收口并形成稳定截点后优先建议交接。这两个数值是本地运行软门禁，不是 OpenAI 官方限制，也不要求你持续盯文件。
13. 规则文档保存在本地时，首次使用、换电脑或移动规则文件夹后，先使用下面的“登记规则文档目录”。以后可以只说“读取 02、03、04、09”，不必反复上传未变化的附件。同一任务内文件未变化时 AI 可复用已读记录；新任务会从已登记路径重新读取适用规则，不要求你重新上传。你也可以直接用自然语言描述目标，不必在每条消息中重复粘贴总指挥提示词；AI 应先自动判断任务类型和风险，并从已登记规则入口加载适用规则，只有规则路径失效、状态冲突、责任不清或权限不足时才提出补充问题。自然语言不会自动继承旧授权，也不能覆盖团队硬规则。
14. 你选择的场景只是意图提示，不是事实结论。每次启动场景 2B 时，AI 都要先只读判断场景是否适用；高置信度的低风险误选可以在回显理由后自动纠正，涉及责任接管、远端写入、历史覆盖或基线不可靠时必须停下来请你确认。
15. 本地修改、本地测试和本地 Commit 不会自动送到 GitHub；只有 Push、创建或更新 Issue/PR、Comment、Review、Approve、Merge 等动作才会改变远端。确认本地执行卡不等于授权任何远端写入。
16. “本地闭环”不是“不看远端”。新目标仍要从可信的当前主线和仓库规则开始；已有远端协作记录的目标还要继承相关 Issue/PR、Base/Head、Review、责任和未闭环意见。
17. 短迭代可以暂不 Commit；任务较长、准备人工验收、同步主线或切换阶段前，AI 应建议建立可恢复的本地 Commit 检查点。不得清理、覆盖或夹带来源不明的本地修改。
18. AI 自检和你的人工验收可以减少返工，但不能冒充仓库明确要求的独立 Reviewer、CODEOWNER 或专业验收。最终是否还需要另一位队友审阅，以当前 PR 作者、Base 门禁、分支保护、最后 Push 后批准规则和团队约定为准；参与他人 PR 的修复本身不自动使你失去 Reviewer 资格。
19. 面对现有 PR 时，你不需要自己判断该发 Comment、Request Changes，还是直接修改，也不需要自己选择原分支或新分支。AI 必须根据母目标、仓库规则、PR 作者、有效 Reviewer 资格、合并风险、责任、并行修改、权限和问题确定性自动推荐，并用几句话解释“选择什么、为什么、为什么不选主要替代方案、修复后当前处理者能否有效 Approve；不能时由谁复审”。涉及远端写入或责任接管时仍须你确认。
20. Comment 和 Request Changes 不是推进任务的必经步骤。能够安全直接修复、不需要立即阻止当前 Head 合并，且修复后当前处理者仍可按仓库规则有效 Approve 时，优先推荐“直接修复、验证当前 Head、Approve”，避免让队友重复理解和实现同一方案。只有确有信息传递、协调或合并门禁价值时才建议 Comment 或 Request Changes。
21. 一张执行卡写“本阶段仅复审”不代表整个推进目标已经变成纯复审。AI 必须同时保留母目标和当前阶段：如果母目标是把 PR 推到可合并状态，复审结束后仍要自动给出本地实现候选卡、责任交接或真实阻断，不能等你重新想到并提出“我来修”。
22. GitHub 禁止 PR 作者批准自己创建的 PR；但非 PR 作者的 Reviewer 向该 PR 提交修复后，是否仍能有效 Approve，要读取当前仓库和 Base 的实际规则。团队未要求“实现者独立复审”或“最后 Push 后由另一人批准”时，不得自行加码制造等待；高风险改动可以建议第二人复核，但必须明确它是风险建议还是硬门禁。
23. 长任务默认采用低干扰模式：允许执行更慢，但避免同时运行多个构建、完整测试、模型或浏览器任务。AI 不承诺持续控制 CPU/内存百分比；浏览器自动化默认无头单 worker。执行前已经知道需要可见窗口时，AI 应写入执行卡或启动摘要；运行中临时发现需要时可以直接打开并继续，不等待你的回复，验证后关闭。
24. 总指挥的“当前进度视图”同时是账号断联后的灾难恢复热快照。AI 应在长任务开始前、会改变恢复路径的阶段边界和每个独立批次结束后低频更新；不是每发一条消息都写，也不复制聊天、截图、完整日志或 Diff。例外专项任务只更新自己负责路径下的短状态或向总指挥回传增量。
25. 新账号完全没有聊天历史时，不需要手工重述项目。先在目标项目新建任务，发送下面的“场景 1A：空白账号灾难恢复”；AI 必须先只读恢复，不能把旧快照中的 Push、Review、Approve、Merge、部署或专业确认当作新任务授权。
26. 本地连续开发后不需要你自己预先把每次修改切成远端 PR。人工回归尚未完成时，也可以先做不产生发布就绪声明的“发布归属预审”；AI 读取本地 Commit、文件和代码块，建立“本地变更 → 现有 Issue → 现有 PR Head”的归属矩阵。技术提交边界与团队责任边界不一致时，可以从保留的存档分支向不同目标 PR 分别移植。没有可靠现有载体且你禁止新建 Issue/PR 时，该部分保留本地并停止，不会勉强塞进名称相似的对象。
27. 图片较多的人工核验按“大轮次”管理。只有预计原图会长期挤占主窗口、结构化结果足以支持后续工作，且隔离收益明确大于新建任务和交接成本时，才在轮次开始前建议一个“视觉验收观察任务”；少量截图和需要与当前代码连续对照的反馈继续留在总指挥。采用隔离时，一个大轮次最多一个观察任务，不按图片或小阶段拆分。A 轮关闭后，AI 再写结案摘要和截图清单，把 A 原图设为默认不回读；这不是删除证据，真正删除仍需你另行确认。
28. 全量远端推进的耗时应按实际工作分类说明：只读扫描和协作元数据动作通常较短；包含代码同步、修复、Push 和当前 Head CI 时属于交付型推进；包含浏览器、模型或设备矩阵时属于高资源推进。AI 应在执行卡中给出基于仓库历史的估计区间和主要关键路径，但这不是硬时限。交付型推进首次 Push 前应先运行与受影响 CI 等价的本地门禁，CI 等待期间并行处理不依赖结果的只读核账，以减少第二次 Push/CI 和纯等待。

### 长任务期间保持电脑可用

- 你可以在 AI 执行长任务时继续编辑文档或浏览网页。默认优先保持前台可用，而不是追求最快完成。
- “后台运行”只能避免窗口抢焦点，不能单独降低资源占用；AI 还必须限制浏览器 worker，并让构建、完整测试、模型和 GPU 验证依次执行。
- 必须观察真实页面且执行前已经可以预见时，AI 会在执行卡或启动摘要中告诉你。运行中临时发现需要可见窗口时，告知只是一条非阻断通知，AI 可以直接打开并继续，不把它变成新的确认步骤。普通自动回归仍应使用无头模式。
- 如果你感到明显卡顿，直接说“暂停新的重型步骤并切换低干扰模式”。AI 应先保存断点、回收自己创建的空闲窗口和服务，再以单 worker、最小测试范围继续；不会结束你的个人或系统进程。

快速定位：

| 现在要做什么 | 直接使用 |
| --- | --- |
| 首次使用、换电脑或移动了规则文件夹 | 登记规则文档目录 |
| 首次启动或恢复总指挥 | 场景 1 |
| 新账号完全没有历史，或旧总指挥任务无法继续 | 场景 1A |
| 提出普通开发目标 | 场景 2 |
| 把会议、问题或规划转为 Issue，并继续实现到 PR | 场景 2A |
| 从一个新的独立目标开始，在本地多轮实现和人工验收后再集中发布 | 场景 2B，子场景 A |
| 把已经在远端协作过的目标从当前断点转为本地闭环 | 场景 2B，子场景 B |
| 全量接管当前协作队列中的 Issue/PR | 场景 3A |
| 只检查协作队列的新对象、新回应、代码变化和历史漏项 | 场景 3B |
| 在新任务中精确解释上一轮某个 Issue/PR | 场景 4B |
| 汇总进展、人工操作、目标变更、交接或复盘 | 场景 4～7 |
| 立即暂停 | 场景 8 |

全量推进适合首次接管、范围或协作者变化、长期未处理、怀疑遗漏或历史截点不可靠时，用来重建当前完整协作队列。增量推进适合已有可靠截点后的高频交替协作，只检查新增/变化对象、未闭环旧账、派生对象和最小依赖；它不是只看新编号。任务数量少不等于可以直接增量，新开任务也不等于必须全量，关键看可靠截点能否恢复。拿不准时可以直接使用场景 3B，由 AI 验证截点，不可靠时自动转为全量。

场景 2B 适合某个功能由你承担主要实现责任、希望先在本地连续迭代，等人工表现和自动验证都稳定后再集中发布。拿不准是子场景 A 还是 B 时保持“自动判断”；如果目标同时包含新功能、已有 PR 和队友负责的依赖，AI 应拆成多个工作包，不能强行把整个目标归入一个子场景。

账号、范围门禁、责任判断、远端授权、语言和输出细则由核心规则统一维护；操作手册不重复展开。使用者本人、本轮协作成员或其他 AI 的建议都要先核对事实和风险，不能直接当成成立的结论。

## 首次使用、换电脑或移动目录：登记规则文档目录

只有首次使用、规则文件夹被移动或换电脑时需要执行一次。请复制下面内容，把路径替换成当前存放 `00～10` 文档的文件夹；平时执行场景 2A、2B、3A、3B 等任务时不必重复填写。

```text
第二代规则文档目录：【本地绝对路径】(Windows 示例：C:\path\to\codex-workflows；macOS/Linux 示例：/path/to/codex-workflows)
请验证该目录包含《00-第二代工作流总览.md》，并按其中编号注册表核对规则文件。验证通过后，把新的规则根目录、注册表版本和逐文件指纹写入当前项目的 AI 状态索引；旧路径标记为失效。只登记规则入口，不修改产品代码，不执行远端写操作。
```

预期结果：AI 明确回复“规则目录验证通过并已登记”，列出识别到的规则版本和缺失文件。若路径不存在、目录不完整或状态索引不可写，AI 必须停止登记并说明具体问题，不能假装成功；你只需提供新路径或修复后的文件夹，不必逐个上传文档。

## 场景 1：首次启动或恢复总指挥

读取文档：按 `02` 的标题级加载映射读取不可压缩内核，并读取 `09` 核心原则和 `10` 的规则入口/当前指针章节；影响范围不可靠时才全文回退

复制发送：

```text
第二代规则文档目录：【自动定位 / 本地绝对路径】(Windows 示例：C:\path\to\codex-workflows；macOS/Linux 示例：/path/to/codex-workflows)
首次使用、换电脑或移动过规则文件夹时填写当前绝对路径；其他情况保留“自动定位”。
请按 02 的标题级加载映射读取 02、09、10 的启动内核，在当前项目建立或恢复唯一总指挥；记录实际读取标题，影响范围不可靠时再全文回退。优先从项目状态索引登记的本地规则根目录读取；入口缺失时再请我提供一次规则文件夹路径，不要要求我逐个重复上传规则附件。
先只读确认项目范围、规则入口、当前目标、现有任务、代码/Git 状态和远端状态。
判断这是首次启动、正常恢复、目标变更还是控制面冲突。
不要修改产品代码，不执行远端写操作，不创建重复状态记录。
最后只汇报：当前目标、事实基线、活跃任务、阻断、下一波次和需要我确认的事项。
```

## 场景 1A：空白账号灾难恢复

适用情况：新账号看不到任何旧任务，或虽然能看到旧对话但无法继续发送消息。你只需要在真正的目标项目中新建一个 Codex 任务，并复制下面一段；不需要先找旧任务 ID、历史卡片 ID 或逐条解释项目。

读取文档：先从项目规则定位总指挥入口，再读取当前进度视图、`AI状态索引.md`，并按恢复缺口读取第二代 `02、04、09、10` 对应章节；影响范围不可靠时全文回退。

```text
我现在明确任命你为本项目的新总指挥。请执行一次“空白账号灾难恢复只读接管”。
```

不要为八个小阶段开八个任务。少量图片、需要与代码修改连续对照或结果卡不足以替代原图时，继续使用当前总指挥任务。只有长寿命主窗口会被大量原图显著拖累且隔离净收益明确时，才采用“长寿命总指挥保持文字主线 + 当前大轮次一个短寿命视觉观察任务”。两种路径都依赖稳定断点；单纯把本地索引标成不读取，不能抹掉当前聊天已经上传的图片。

#### 在图片进入总指挥聊天前使用视觉观察任务

如果预计本轮会连续上传多张截图、原始分辨率图片或视频，不要先把它们发给长寿命总指挥。先让总指挥生成本轮文字测试包，再新建一个 Codex 任务，将下面提示词和测试包发给它；一个大轮次只开一个观察任务：

```text

请读取总指挥提供的文字测试包：【粘贴测试包，或填写其稳定本地路径】
本轮 ID：【由总指挥生成】
当前代码/页面基线、URL 与工作区：【由测试包给出】

1. 每批先按步骤 ID 记录可直接观察到的事实、通过/失败/待确认、证据 ID 和仍需补充的最小信息；不要猜测代码根因或医学参数。
```

操作：截图只发到该观察任务；结束后把“视觉结果卡正文或稳定路径”发给总指挥，不要再次上传整批原图。目的：让原图只停留在短寿命观察任务中，避免长期累积在总指挥聊天。预期结果：总指挥能够仅凭结果卡继续记录、判断和修复；只有结果卡冲突、信息不足或触发安全/专业复核时才点名回查最少原图。异常处理：如果观察任务无法读取测试包、基线不一致、结果卡无法写入或图片证据与步骤无法对应，停止该轮并把错误文字和受影响步骤 ID 发给总指挥。

已经上传到总指挥聊天的旧图片不能由这套流程追溯移除。当前轮尚无可靠断点时先完成最小结案，不为迁移而丢失未持久化反馈；从下一个稳定大轮次开始使用观察任务。

### 3. 发布归属预审、正式发布候选或紧急发布豁免

想先核对现有 Issue/PR 归属时选择“发布归属预审”；自动验证和人工表现都达到可接受状态时选择“正式发布候选审查”；只有时间或业务确实紧急、你决定不完成原定人工验收并愿意承担已知剩余风险时，才选择“紧急发布豁免审查”。紧急豁免不是“验收通过”，不能绕过 Required Checks、有效 Review、权限、安全、隐私或平台保护。

```text
请按场景 2B 执行“既有 Issue/PR 归属发布”的对抗式审查和事实回读。

发布审查阶段：【发布归属预审（允许人工回归未完成） / 正式发布候选审查（自动验证和人工表现均已接受） / 紧急发布豁免审查（明确放弃未完成的人工验收并接受风险）】
紧急豁免原因：【不适用 / 时间或业务紧急原因】(示例：必须在今天完成团队集成，无法继续安排原定人工回归)
未完成的人工验收与风险接受：【不适用 / 逐项列出未完成验收，并明确接受这些未验证表现进入本次发布】(示例：未完成真实照片的最终交互回归；接受仍可能存在局部视觉或交互缺陷，但不得宣称临床验证)
发布对象策略：【只使用现有 Issue 和现有 PR，禁止新建 / 允许在没有可靠载体时建议新建，但本轮仍不创建】
本地候选范围：【自动读取当前安全存档分支尚未远端交付的全部本地 Commit 和已跟踪修改 / 指定 Commit 范围】(示例：自动读取；或 abc123..def456)
明确排除：【无 / 不得进入发布范围的目录、文件或工作包】(示例：本地截图、浏览器会话目录和个人证据记录)
远端动作授权：【先生成执行卡并等待确认 / 只执行 Push / 执行 Push、更新现有 PR、请求 Review并等待 / 本消息同时最终确认下方精确终态动作】
精确终态动作：【无 / 逐项写明允许的 Auto-merge、Approve、Merge、Close 及适用条件】(示例：Required Checks 全绿且取得仓库要求的有效批准后，允许现有 PR Auto-merge；禁止管理员绕过、Force Push 和直接写默认分支)

本轮事实回读的目的不是重复验收代码，而是确定每一部分代码的正确远端载体和执行门禁。请读取最新默认分支、现有 Issue/PR、Base/Head、PR 作者与责任、分支可写性、继承 Review、未闭环意见、冲突、Checks/Actions、Auto-merge 和当前账号权限；同时核对本地存档分支、完整 Commit 链、未提交/未跟踪内容、测试和人工验收证据。若选择预审，必须如实列出尚未完成的发布门禁，并把执行卡标成“草案、不可执行”；若选择正式审查但证据不足且没有有效紧急豁免，自动降级为预审。若选择紧急豁免，必须把原因、未完成验收、风险接受、回滚/停止条件写入执行卡和目标 PR；不得把未完成写成已通过，也不得豁免仓库或平台硬门禁。

建立“发布归属矩阵”：以本地 Commit、文件或必要的代码块为最小候选单元，逐项映射到现有 Issue 和实际承载代码的现有 PR Head，写明匹配依据、置信度、重叠/冲突和不匹配项。标题、标签、编号相近或文件名相同不能单独证明归属。一个 Commit 可以拆到多个 PR，多个 Commit 也可以合入同一 PR；Issue 只记录需求/责任，代码必须进入对应 PR Head。

保护当前存档分支和 Commit 链，不得 Force Push、Reset、重写或把拆包结果覆盖回唯一存档。若需要多目标发布，请为每个目标 PR 从回读后锁定的最新 Head 建立独立本地 worktree/分支；整颗 Commit 归属明确时可计划 Cherry-pick，跨对象时按文件或代码块移植并生成目标分支的新 Commit。此阶段只规划，不实际改写本地历史。

若发布对象策略禁止新建，而某部分没有可靠匹配的现有 PR、目标 PR 已关闭/合并且不可继续、分支不可写、责任冲突或正在发生同范围并行修改，请把该部分保留在本地并标记阻断，不得勉强归入相似对象，也不得创建新的 Issue 或 PR。

请输出：本地最终变更与准确 Commit 范围、发布归属矩阵、默认分支和各目标 PR 的最新 Base/Head、责任/权限/Review/Checks/冲突状态、验证与人工证据、未匹配或暂留本地项、剩余风险，以及一张最小远端发布执行卡；选择预审时必须明确称为“不可执行草案”。执行卡必须把本地拆分准备、Push、更新现有 PR 正文、Issue/PR Comment、回应 Review、请求 Review、CI 重跑、启用 Auto-merge、Approve、Merge、Close 分别列出目标、动作、授权状态和失效条件；没有必要的动作明确写“无”。

如果“远端动作授权”选择等待确认，先不要执行任何远端写入，也不要执行会改变本地历史的拆分/移植；等我确认后只执行获批动作。如果选择“本消息同时最终确认下方精确终态动作”，且对象、动作、条件和禁止项已经明确，则本消息同时构成远端执行卡确认，可以连续执行本地移植、Push、更新现有 PR、请求 Review，并在精确条件满足后执行已列终态动作。未列出的 Merge、Approve、Close、Auto-merge、Issue/PR 新建或部署一律未授权；Base/Head、范围、权限、Required Checks 或 Review 门禁漂移时只暂停受影响动作，不得绕过。
```

怎样使用这个模板：通常只需选择一个“发布审查阶段”，填写你真正决定的业务字段；Commit、Base/Head、PR 编号和执行卡 ID 由 AI 回读，不需要你查。正常发布把紧急字段填“不适用”；紧急发布必须把“为什么跳过、跳过什么、接受什么风险、最终允许做到哪里”四件事写清楚。想一条消息直接执行时，必须选择“本消息同时最终确认”并把终态条件写完整，不能只写“自动提交、合并等等”。

场景切换的判断标准：

1. 远端仅有需求讨论，不存在实现分支、PR、明确负责人或未闭环 Review 时，可以把需求作为证据后按子场景 A 建立新的本地实现包。
2. 已存在实现 PR、活跃分支、明确负责人、Review request、未闭环意见或队友新提交时，必须使用子场景 B 或拆分混合场景。
3. 对象由使用者本人负责时，可以在隔离分支本地续作；是否继续更新原 PR，要等发布前核对当前 Head、分支权限和团队规则。
4. 对象由他人负责时，AI 先判断直接修复是否比交棒更高效且不会扰乱并行开发。没有可核验交接或明确授权时，不得直接写入对方分支；但在团队规则允许、问题明确可复现、没有同范围并行修改且本地执行卡已确认时，可以在本人隔离修复分支上实现并验证候选方案。该动作不改变 Assignee、长期责任或远端权限；发布前再按团队规则选择补丁 PR、交付 Commit 或请原作者吸收。若需要作者专属背景、产品决定或正在发生同范围修改，则交回原作者并说明恢复条件。
5. 当前工作区存在来源不明、与目标混杂或无法恢复基线的修改时，先进入恢复场景：识别归属、保存证据并隔离目标，不能直接开始 A 或 B。
6. 最终发布继续使用现有远端授权规则；本场景不会绕过仓库明确要求的独立 Review、Required Checks、CODEOWNERS 或管理员门禁，也不会把风险建议伪装成仓库硬规则。

```text
请汇总当前轮次中所有需要【使用者本人】参与的事项，并生成一份可直接照做的批量人工操作清单。
先排除 AI 能自动完成的步骤；其他团队成员、领域专家或管理员的事项只列为外部门禁，不混入我的操作清单。
按优先级和依赖顺序排列；相同操作可以合并，但必须保留每个 Issue、PR 或任务的独立状态，并使用“对象类型+编号”避免同号混淆。
每组操作说明：关联对象、参与类型、是否阻断、推荐方案、最少步骤、目的、预期结果、异常时需要的截图/日志/现象，以及完成后可直接复制的批量反馈模板。
已能从项目、平台或状态索引读取的信息请自动预填，不要要求我查找技术 ID 或重复填写环境信息。
```

完成一批人工操作后，复制发送：

```text
以下是本轮人工操作反馈，请读取并更新每个对象的独立状态；单项失败、未执行或证据不足不得被推定为通过，也不得暂停其他独立对象。

证据附件根目录：【无 / 本地绝对路径】(Windows 示例：C:\path\to\evidence；macOS/Linux 示例：/path/to/evidence)
共同说明：【无 / AI 无法从附件和项目中判断的补充】(示例：所有截图均来自同一次测试)

【Issue / PR / 任务 + 编号】
- 结果：【通过 / 失败 / 部分通过 / 未执行】
- 实际观察：【无补充 / 观察到的现象】(示例：点击后页面无响应)
- 证据位置：【无 / 对应子目录或文件名】(示例：issue-1/error.png)
- 额外说明：【无 / AI 无法自动判断的信息】(示例：本次使用移动网络测试)

请自动核对附件与编号的映射、判断证据是否足够、更新阻断和恢复条件，并继续所有能够自动推进的事项。只有确实还需要我参与时，才重新生成最小人工操作包和可复制提示词。
```

对象很多时可以把重复块改成紧凑表格：`对象｜结果｜实际观察｜证据位置｜额外说明`。AI 应预填对象列表，使用者本人只补观察结果；没有反馈的对象保持“未反馈”，不得按通过处理。

附件目录建议：每一批人工操作建立一个独立根目录，例如 `人工反馈/<YYYYMMDD>-本轮/`，再按 `issue-<NUMBER>`、`pr-<NUMBER>`、`task-<TASK_ID>` 建立子目录；多个对象共用的证据放在 `shared`，并在反馈中写明覆盖哪些对象。文件可用 `01-before.png`、`02-after.png`、`error.png`、`notes.txt` 等简短名称。只需把本批次根目录的绝对路径发给 AI，不必逐个上传；AI 先建立或读取本轮清单，只打开与当前步骤和结论有关的文件，不默认递归分析整批旧附件。

不要只用数字命名子目录，否则 Issue 和 PR 同号时会冲突。含个人数据、受监管数据、账号、密钥或其他敏感信息的附件应先脱敏，默认放在仓库外；确需放入项目目录时只能使用项目已忽略的调试目录，并确认不会被 Git 提交。系统临时目录中的文件可能自行失效，AI 必须在清单中标记“临时来源”，但不得擅自把含人脸材料复制进仓库。附件只能作为证据，不能因为文件存在就自动判定测试通过。

## 场景 4B：在新任务中解释上一轮某个对象

总指挥提醒适合分流时，打开一个新任务并复制下面提示词；也可以明确要求当前 AI 创建新任务。这样做的目的是让原总指挥继续推进主线，同时让新任务只读取目标对象的短回执和当前事实。

```text
请从项目总指挥入口恢复与【对象类型 + 编号】有关的最近可靠执行回执和 GitHub 当前事实，只读解释：上一轮实际做了什么、为什么这样做、哪些替代动作没有采用及原因、原结论是否因新事实失效、当前行动方和下一步。
只读取该对象的决策回执、证据指针和验证结论；不要重读无关聊天、附件、历史或 Diff。不要修改代码、中央状态或远端平台。
如果找不到完整的可迁移决策回执，明确告诉我回到原总指挥补录，不要根据零散历史猜测。
```

预期结果：新任务能独立解释该对象，又不接管主线。若它报告回执缺失、事实冲突或截点失效，把报告发回原总指挥补录或重新核验；不要让两个任务同时写中央状态或执行同一对象。

## 场景 6A：新总指挥接收正常交接

适用情况：旧总指挥仍可用，并且已经按场景 6 生成了通过稳定检查的正式交接记录或便携快照。它不同于场景 1A：场景 1A 用于旧任务不可读、不可写或根本没有可靠交接材料的灾难恢复；场景 6A 用于有明确交接记录的正常换任。

在新账号的目标项目中建立一个新任务，把交接记录作为附件提供，或把它的本地绝对路径填入下方提示词。不要只说“你接着做”，也不要在第一次消息中授权它继续旧队列。

读取文档：交接记录指定的项目规则和状态入口，以及 `总指挥轻量交接启动配置.md`。新任务必须完整读取该配置并建立自己的加载记录；配置和 02、04、07、09、10 的来源指纹全部匹配时，候选阶段不再全文读取五份编号规则。任一指纹异常时只展开受影响规则；配置缺失、来源清单不完整或影响范围不明时退回完整读取。

第一次发送：

```text
我现在明确指定你为本项目的“新总指挥候选”。请读取下面的正式交接记录，并执行一次正常交接的第一次只读接管：
交接记录或便携快照：【本地绝对路径 / 已附附件】

本轮只做接管核验，不开始新的全量、增量或专项调度。先按交接记录定位项目入口、当前进度视图、AI 状态索引和第二代规则根目录，并由你自己完整读取 `总指挥轻量交接启动配置.md`、核对其 SHA-256 及 02、04、07、09、10 的来源指纹；只有异常项才展开对应编号规则，无法确定影响范围时退回完整读取。不得继承旧任务的规则已读状态、远端授权、运行中进程、完成声明或专业结论。

只读核对：交接快照是否仍在有效期内、旧总指挥世代与单写者状态、当前目标和精确断点、工作区/分支/worktree/未提交修改、代码与 Git/GitHub 基线、验证证据入口、阻断、禁止项、恢复条件和失效条件。默认只输出分支、Head、状态计数、聚合指纹和 PASS/WARN/FAIL；不读取完整旧任务、Git 路径清单、Diff、日志或冷截图，只有冲突项才最小展开。已有完成凭证的任务不得重复执行；发现事实漂移时只标记受影响范围、证据和最小补救动作。

核对完成后，先回复：恢复置信度、已确认事实、待确认或冲突项、交接是否达到可切换条件、拟登记的新总指挥世代/任务 ID/接管截点。事实可靠时可以写入“候选接管截点”，但在我明确确认切换前，不得终止旧总指挥，不得取得中央调度权，也不得执行产品代码或远端写操作。
```

预期结果：新任务应明确说自己当前只是“新总指挥候选”，给出聚合核验依据和候选接管截点，并等待你先停止或归档旧总指挥、再做最后一次切换确认。若交接记录缺失、规则指纹变化、Git/平台事实冲突或存在另一个调度者，它必须保持只读并列出最小缺口。

当新任务明确报告“已达到可切换条件”后，再发送：

```text
我已停止或归档旧总指挥，并确认将本项目总指挥调度权切换给你。请先最小复核轻量启动配置/来源指纹、中央世代与单写者、候选截点失效条件、工作区聚合指纹和当前远端基线；仍可靠时，把候选接管截点升级为正式接管截点，登记新的唯一总指挥世代和当前任务 ID，并把旧总指挥标记为已停止调度但保留全部历史。回读更新后的项目入口、当前进度视图和 AI 状态索引，确认单写者唯一、旧授权未继承，然后只从交接记录中的精确断点继续。未包含在我当前明确指令里的产品代码修改和远端写操作仍未授权。
```

只有旧总指挥已由操作者停止或归档、第二段确认发出、切换前最小复核通过且中央状态回读一致后，换任才算完成。第一段只建立候选身份和只读接管，不转移调度权；候选不得自行终止旧任务。

如果只是临时交给其他 AI 执行一段任务、不转移总指挥权限，把生成的便携快照连同下面提示词发给它：

```text
请把附件视为有失效条件的只读交接快照，先核对项目规则、当前代码和远端事实，再处理我明确交给你的范围。
当前总指挥仍是中央状态的唯一写入者；不要直接覆盖中央进度、拓扑或状态索引。
你可以更新收到的便携交接快照副本。结束时返回：更新后的快照、实际完成、代码/远端变化与回执、验证、未完成项、阻断、下一责任人，以及可由总指挥核验写回的状态增量。
任何远端写操作仍须遵守当前项目规则和本轮精确授权。
```

## 远端协作授权：默认由 AI 生成

```text
请根据只读扫描结果自动生成一张最小批量执行卡，自动填写卡 ID、精确对象、当前 Base/Head、允许动作、分支、验证、禁止项、有效期、失效条件和失败回退。
把最终确认文本一并生成给我复制；我只负责确认、拒绝，或补充 AI 无法决定的限制。
```

确认文本可直接写“我确认刚刚生成的批量执行卡，按卡内边界执行”。只有同时存在多张待确认卡时，AI 才在文本中自动带入对应卡 ID；不得要求使用者本人手工查找。对象必须扫描后才能确定时，不填写猜测编号。

批量执行卡的正文必须让非专业使用者也能判断，固定先写：AI 推荐、为什么、最坏可能结果、仓库硬保护、授权后会自动做什么、明确不会做什么、什么情况下自动跳过。编号、Base/Head、分支和精确 Review 内容放在附录，不用它们替代人话风险说明。

只有人类、项目规则或平台真实授予的权限才有效。AI 的自动预填和历史授权记录不能替代本轮最终确认。
